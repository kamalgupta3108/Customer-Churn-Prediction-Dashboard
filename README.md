# Customer Churn Prediction — ML Core

Predicts which customers are likely to churn, using the IBM Telco Customer
Churn dataset (7,043 customers). This is the ML foundation for a full-stack
churn prediction dashboard (backend API + React frontend coming next).

## Problem

Telecom companies lose revenue when customers cancel their subscription
("churn"). If we can predict *who* is likely to churn and *why*, the business
can proactively intervene (offer discounts, fix service issues, etc.) before
losing the customer.

## Dataset

- Source: [IBM Sample Data Sets](https://raw.githubusercontent.com/IBM/telco-customer-churn-on-icp4d/master/data/Telco-Customer-Churn.csv) — 7,043 customers, 21 features
- Target: `Churn` (Yes/No) — **26.5% churn rate** (imbalanced)
- Features: demographics (gender, senior citizen, partner, dependents),
  account info (tenure, contract type, payment method, charges), and
  subscribed services (internet, phone, streaming, tech support, etc.)

## Approach

| Step | What / Why |
|---|---|
| Data cleaning | `TotalCharges` was stored as text with blank values for new customers (0 tenure) — converted to numeric, filled blanks with 0 |
| Encoding | Label-encoded categorical features; acceptable for tree models, a documented simplification for Logistic Regression (see note below) |
| Scaling | `StandardScaler` on numeric features (tenure, charges) — needed for Logistic Regression, harmless for Random Forest |
| Imbalance handling | `class_weight='balanced'` on both models instead of over/undersampling — no synthetic data, no data loss |
| Models compared | Logistic Regression (interpretable baseline) vs Random Forest (captures feature interactions) |
| Model selection | Chose by **F1-score on the churn class**, not accuracy — accuracy is misleading when 73% of customers don't churn anyway |

## Results

| Model | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|
| Logistic Regression | 0.505 | 0.797 | 0.618 | 0.840 |
| **Random Forest (selected)** | **0.539** | **0.762** | **0.631** | **0.841** |

**Recall was prioritized over precision** — in churn prediction, failing to
flag an at-risk customer (false negative) is usually more costly to the
business than a false alarm (false positive), since a false alarm just means
an unnecessary retention offer, while a missed churner is lost revenue.

### Top churn-driving features
1. **Contract type** (month-to-month customers churn far more — no lock-in)
2. **Tenure** (newer customers churn more)
3. **TotalCharges**
4. **OnlineSecurity**
5. **MonthlyCharges**

## Known limitation / next improvement

Label encoding imposes an artificial order on non-ordinal categories (e.g.
`PaymentMethod`). This doesn't affect Random Forest (splits on thresholds,
not magnitude) but is a theoretical weakness for Logistic Regression. A
cleaner approach would be one-hot encoding — noted here as a deliberate
scope tradeoff for a first version, not an oversight.

## Running tests

```bash
pytest tests/ -v
```

Tests use an isolated in-memory SQLite database and flush the Redis test
cache before each run, so they never touch real data. Note: you still need
PostgreSQL and Redis running locally, since the app connects to them at
import time (a known simplification for this stage of the project).

## How to run

```bash
pip install -r requirements.txt
python train.py
```

This regenerates the model artifacts in `model/` from scratch, so anyone
cloning the repo can reproduce the results.
